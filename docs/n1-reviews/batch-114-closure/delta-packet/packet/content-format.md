# Content format (EN manifest schema 1; RU manifest schema 2)

The Android app [Ensō Nihongo](https://github.com/stop-cran/kanji-cards-android) reads this repository. Anyone can fork it and
point the app at their fork. `tools/validate.py` checks structural constraints; dictionary accuracy, origins, natural examples,
and useful navigation still require editorial review.

```
manifest.json          generated by tools/build_manifest.py: schemaVersion, contentVersion, SHA-256 per file
kanji/<char>.md        one card per kanji, e.g. kanji/日.md
words/<word>.md        one article per word, e.g. words/大小.md
articles/<slug>.md     free-form articles (no front matter required)
strokes/<char>.json    generated by tools/generate_strokes.py from KanjiVG
counters/<id>.json     v1 suffix/reverse or v2 whole expressions (manifest files map)
scenes/<word>.json     optional named scene catalog (separate manifest scenes map)
images/<name>.webp     scene assets (separate raw-byte-hashed manifest images map)
listening/<id>.json    N5 listening packages (separate manifest listening map)
audio/<id>.ogg         approved mono Opus recordings (separate raw-byte-hashed audio map)
```

## Repository teaching language

`content-language.json` declares exactly `{"baseLanguage":"en","targetLanguage":"ja"}` for this edition,
or `ru`/`ja` for the Russian edition. No declaration is legacy EN/ja. Language is repository-wide and stable
across branches; changing language requires a different repository identity, not relabeling accepted cached lessons.
The generator includes both language fields in `manifest.json` and in its deterministic `contentVersion`.
Malformed/unsupported declarations stop generation/validation; contributors never hand-edit generated manifests.

New EN manifests retain schema 1 so the released EN-only reader can still import this actual newly generated tree.
RU requires explicit language fields and manifest schema 2, which that old reader refuses before importing lessons.
The new reader supports legacy/explicit EN schema 1 and explicit RU schema 2; missing RU declarations or mismatched
schema/language are errors, not permission to fall back to English. Nested stroke/counter/grammar/listening schemas
keep their independent meanings. A shared-tool change must test old-reader/new-EN compatibility and RU safe refusal.

All learner-facing titles, prose, glosses, task help/options/feedback and descriptions follow the base language.
Japanese paths, internal IDs, readings, answers, tags and levels remain stable except for separately reviewed corrections.
RU kanji H2 sections are `Значение и происхождение`, `Чтения`, `Частые слова`, `Примечания`; word sections are
`Значение`, `Как сочетаются кандзи`, `Синонимы и антонимы`, `Оттенки значения`. Kana-only words may omit
the kanji-combination section. RU facts labels are `Черты`, `Ключ (радикал)`, `JLPT`; retain existing EN labels here.
Reading-table semantics remain unchanged and the reader accepts the localized section/table labels.

Legacy counter v1 gloss field `en` remains valid for released EN readers. New-language content uses neutral
`translation`; the updated parser adapts it to the same gloss model. Declaring both fields is invalid.
Do not migrate published EN v1 cards to the neutral field until an explicitly approved APK-first compatibility change.
Other existing `translation`/`gloss` fields are already language-neutral.

Language metadata/provenance do not certify a translation, approve reused media, advance whole-corpus coverage or
authorize generation. Use the [RU checkpoint plan](https://github.com/stop-cran/learning-japanese-ru/blob/main/docs/IMPLEMENTATION-PLAN.md).

## N5 listening

The [listening authoring and schema guide](listening-n5.md) specifies original short dialogues/monologues, exactly three
questions per passage, four stock voices, mild N5 pacing, optional context images and hash-bound final-recording approval.
Listening difficulty includes essential spoken vocabulary and speech demands, not written kanji lists or grammar alone.
Draft JSON without audio is valid but unavailable for scoring. Never treat automated validation as actual listening approval.
Run `tools/check_content_budget.py` as well as validation and manifest regeneration before publishing media.

Japanese [task packages](listening-tasks.md) use separate `listeningTasks`, `listeningTaskAudio`
and `listeningTaskImages` maps. Schema 1/policy 1 requires integer JLPT 5; the [N4 extension](listening-n4.md)
requires schema 2/policy 1/integer JLPT 4 without changing the four stage/choice shapes.
Legacy English-question packages remain N5-only. Versioned support does not approve a recording
or enable an unfinished diagnostic profile; exact package/media approval and publication gates remain mandatory.

## Numbers & counters

[Counter schema, coverage and authoring](counter-n5.md#version-2-transport-and-future-authoring)
specify separate v1 and v2 files, full written answers, canonical-expression readings, bounded alternatives
and Everyday/Time groups. Keep legacy suffix grading intact. Do not reuse its numeral arithmetic in
new writing/reading modes, nor confuse alternate written units with readings of the displayed expression.
Publish compatible new files alongside v1 so older clients retain their original exercises.

## Kanji card

Restricted YAML front matter followed by the Markdown article. The app accepts only `key: value` scalars and inline `[a, b]` lists.
Do not use block lists, nested mappings, multiline scalars, inline comments, YAML escapes, or commas inside quoted list items.
For example, `onyomi: [アン]` is supported; a YAML block sequence is not. The parser only removes surrounding quotes; it does not decode escapes.
Use UTF-8 with LF or CRLF line endings. Optional article front matter follows the same flat subset; ordinary Markdown articles do not
need metadata. The validator preserves the app's plain-Markdown fallback rather than treating every opening thematic break as a header.
Mapping-shaped opening blocks are checked as metadata; use `***` for an opening thematic break to avoid that ambiguity.

| Field | Meaning |
| --- | --- |
| `kanji` | The character; must equal the file name. This is the card's stable ID. |
| `title` | Short English meaning used as an answer choice in the meaning quiz; unique across cards. |
| `jlpt` | 1–5 (N5 is easiest). Community study classification, not an official exam syllabus. Follow the [source policy and documented exceptions](jlpt-levels.md); do not infer a level from a missing value. |
| `tags` | Free tags, e.g. `jlpt-n5` (must match `jlpt`), `starter` (the original words-driven starter set), `grade-1`, `pictograph`, `indicative`, `compound`, `phonetic-compound`. Use `structure-unclassified` when a historical structural classification has not been established. Stacks will filter on tags. |
| `strokes` | Stroke count; must match `strokes/<char>.json`. |
| `radical`, `radicalNumber` | The key (radical) and its classical number (1–214). |
| `phonetic` | Optional; a verified phonetic component. Omission means it is not supplied, not necessarily that the character has none. |
| `onyomi`, `kunyomi` | Lists in kana; kunyomi uses `.` before okurigana and `-` for affixes. |
| `quizOnyomi`, `quizKunyomi` | Optional ordered exact-string subsets of the corresponding full lists. Omit for legacy full-list questions; `[]` disables that kind. See [curated reading questions](#curated-reading-questions). |
| `distractors` | The app can omit this field, but authored cards must supply at least two distinct, plausible wrong options with existing cards; never include the card itself. |
| `quiz_exclusions` | Optional inline list of other exact single-character kanji IDs that must not appear together as meaning choices. Omission or `[]` means no authored exclusions. Declare once using a top-level unquoted key; no duplicate, self, missing, unsafe or non-character IDs, or overlap with `distractors`. Requires a kanji-exclusion-aware client; older apps ignore it. |

### Quiz authoring

The meaning quiz displays a kanji and offers other cards' English titles as answers. For new cards, curate **three** semantically
distinct wrong options for the default four-choice quiz. Two remain structurally valid for older cards, but the app fills missing
choices from other cards, preferring shared tags. Exact-title deduplication alone does not establish semantic uniqueness:
different English synonyms can still produce two defensible answers. Keep useful semantic comparisons in the body even when
they are unsuitable as wrong answers.

Kanji-exclusion-aware clients ([Android #132](https://github.com/stop-cran/kanji-cards-android/issues/132)) additionally honor
`quiz_exclusions`, using exact kanji IDs, not word IDs, readings or titles. A declaration on either card excludes that direct pair
both against the target and among chosen distractors, for curated choices and tag/random fallbacks in All, level and custom pools.
Exclusions are symmetric but not transitive: A/B and B/C do not exclude A/C. References must resolve in the complete accepted
source, not the currently filtered pool. A small pool may yield fewer choices, even only the target; the app never restores an
excluded card to fill slots. Exclusions affect meaning choices only, not readings, drawing, membership, ordering or saved progress.

Author a pair only from evidence about the actual displayed labels and ordinary meanings. The observed 剰/冗 fallback ambiguity
motivated this mechanism; it is not automatic synonym discovery or a guarantee for uncurated pairs. Existing older APKs do not
enforce this field. Content depending on it requires the upgraded compatible client; bounded owner-testing acceptance does not
prove compatibility of an older installed app or physical-phone/general-release acceptance.

Editorial review must check the displayed titles against the target's ordinary meanings, not merely look for duplicate strings.
This behavior was checked in [QuizBuilder](https://github.com/stop-cran/kanji-cards-android/blob/8c130a25bdb4e444a80a2f78ef0d11b04bddc12f/app/src/main/java/io/github/stopcran/kanji/core/quiz/QuizBuilder.kt);
larger quizzes or a changed app can still require fallback choices. The validator checks structure, not semantic ambiguity.
