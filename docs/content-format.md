# Content format (schema version 1, draft)

The Android app [Ensō Nihongo](https://github.com/stop-cran/kanji-cards-android) reads this repository. Anyone can fork it and
point the app at their fork. `tools/validate.py` checks structural constraints; dictionary accuracy, origins, natural examples,
and useful navigation still require editorial review.

```
manifest.json          generated by tools/build_manifest.py: schemaVersion, contentVersion, SHA-256 per file
kanji/<char>.md        one card per kanji, e.g. kanji/日.md
words/<word>.md        one article per word, e.g. words/大小.md
articles/<slug>.md     free-form articles (no front matter required)
strokes/<char>.json    generated by tools/generate_strokes.py from KanjiVG
```

## Kanji card

Restricted YAML front matter followed by the Markdown article. The app accepts only `key: value` scalars and inline `[a, b]` lists.
Do not use block lists, nested mappings, multiline scalars, inline comments, YAML escapes, or commas inside quoted list items.
For example, `onyomi: [アン]` is supported; a YAML block sequence is not. The parser only removes surrounding quotes; it does not decode escapes.
Use UTF-8 with LF or CRLF line endings. Optional article front matter follows the same flat subset; ordinary Markdown articles do not
need metadata. The validator preserves the app's plain-Markdown fallback rather than treating every opening thematic break as a header.
Mapping-shaped opening blocks are checked as metadata; use `***` for an opening thematic break to avoid that ambiguity.

| Field | Meaning |
| --- | --- |
| `kanji` | The character; must equal the file name. This is the card's stable ID. |
| `title` | Short English meaning used as an answer choice in the meaning quiz; unique across cards. |
| `jlpt` | 1–5 (N5 is easiest). Community study classification, not an official exam syllabus. Follow the [source policy and documented exceptions](jlpt-levels.md); do not infer a level from a missing value. |
| `tags` | Free tags, e.g. `jlpt-n5` (must match `jlpt`), `starter` (the original words-driven starter set), `grade-1`, `pictograph`, `indicative`, `compound`, `phonetic-compound`. Use `structure-unclassified` when a historical structural classification has not been established. Stacks will filter on tags. |
| `strokes` | Stroke count; must match `strokes/<char>.json`. |
| `radical`, `radicalNumber` | The key (radical) and its classical number (1–214). |
| `phonetic` | Optional; a verified phonetic component. Omission means it is not supplied, not necessarily that the character has none. |
| `onyomi`, `kunyomi` | Lists in kana; kunyomi uses `.` before okurigana and `-` for affixes. |
| `distractors` | The app can omit this field, but authored cards must supply at least two distinct, plausible wrong options with existing cards; never include the card itself. |

### Quiz authoring

The meaning quiz displays a kanji and offers other cards' English titles as answers. For new cards, curate **three** semantically
distinct wrong options for the default four-choice quiz. Two remain structurally valid for older cards, but the app fills missing
choices from other cards, preferring shared tags. It only deduplicates exact title strings: different English synonyms can still
produce two defensible answers. Keep useful semantic comparisons in the body even when they are unsuitable as wrong answers.

Editorial review must check the displayed titles against the target's ordinary meanings, not merely look for duplicate strings.
This behavior was checked in [QuizBuilder](https://github.com/stop-cran/kanji-cards-android/blob/8c130a25bdb4e444a80a2f78ef0d11b04bddc12f/app/src/main/java/io/github/stopcran/kanji/core/quiz/QuizBuilder.kt);
larger quizzes or a changed app can still require fallback choices. The validator checks structure, not semantic ambiguity.

## Word article

Word-header keys must be unquoted, unindented identifiers matching `[A-Za-z_][A-Za-z0-9_-]*`;
whitespace before the colon is allowed. Quoted, escaped, tagged and anchored keys are unsupported, even if a later plain
declaration repeats the same field. This is checked before YAML can decode or collapse duplicate names.
The closing `---` delimiter may have trailing whitespace or a whitespace-separated `#` comment; this exception does not allow
inline comments on fields. A prefix such as `---notes` is not a closing delimiter.

| Field | Meaning |
| --- | --- |
| `word` | The word as written; must equal the file name. |
| `reading` | Kana reading. |
| `title` | Short English gloss. |
| `jlpt` | Optional integer 1–5 identifying the word's sourced community vocabulary level, independently of its kanji. Declare it once at the top level with an unquoted key and number. Omit when no level is established; do not use a blank, `null`, a quoted number, a duplicate declaration, or an inferred level. |
| `type` | `kango`, `wago`, `jukujikun` or `gairaigo`. Mixed on+kun words (e.g. 円高 えんだか) have no type of their own: use `kango` for an on-first compound and say in the body that it is mixed (jūbakoyomi). |
| `kanji` | Every distinct kanji occurring in the written word, including characters whose cards have not been added. Use `[]` for a kana-only spelling. Do not omit a character merely to avoid a missing-card reference. |
| `tags` | Free tags. |
| `quiz_distractors` | Optional inline list of up to 3 other exact `word` IDs that make good wrong choices for this word (plausible but clearly different, e.g. 今日 vs 今朝). Used first, before the automatic tag/kanji scoring, in both directions. Must exist, must not repeat, include the word itself, or overlap `quiz_exclusions`. Omission means automatic choices only. |
| `quiz_exclusions` | Optional inline list of other exact `word` IDs that must not appear together as quiz choices. Omission or `[]` means no curated exclusions. Use one top-level unquoted key; reject duplicate declarations, repeated/self IDs and missing targets. |
| `image`, `image_scene` | Optional, given together. `image` is a flat `images/<name>.webp` path (WebP, at most 100 KiB, used by one word only); `image_scene` is the English description shown as alt text and after answering. Scenes must contain no text, kana or letters. Images are generated with `tools/generate_images.py` (prompts in `tools/image_prompts.json`) and listed with raw-byte hashes under `images` in `manifest.json`. |

Body: meaning and usage, how the kanji combine, synonyms and antonyms, and the distinctive nuance.
For kana-only words (`kanji: []`), the `## How the kanji combine` section is optional: omit it unless there is a spelling or
word-formation point worth making. The other three sections remain required, in order.

Vocabulary-aware app versions use an explicit word `jlpt` first. For legacy articles without this field, they retain the previous
fallback based on the hardest known written kanji; that fallback is not a vocabulary-level source. Earlier app versions ignore
word `jlpt` and always use the kanji-based calculation. N4 word study includes N5; N3 word study includes N5 and N4.
Unlike kanji cards, word articles do not require a matching JLPT tag; `tags` remain free study metadata.

The word quiz also uses `title` as the English answer label. The earlier
[candidate builder](https://github.com/stop-cran/kanji-cards-android/blob/8c9713f77083a1ff8b10b5ccb4438b51f0231fec/app/src/main/java/io/github/stopcran/kanji/core/words/Words.kt)
deduplicates exact titles and written forms, not semantic equivalents. Related tags, word type and shared kanji influence candidate
selection. Check glosses against actual meaning and register; different English wording alone does not make two synonyms valid
opposing choices. Do not distort a word's meaning merely to make its title look unique.

Exclusion-aware app versions additionally honor `quiz_exclusions`, for example `quiz_exclusions: [気分]` on 気.
That pair is excluded in both directions even if only one article declares it. Exclusions also apply between other choices
within a question, in both Japanese-to-English and English-to-Japanese quizzes. They are pairwise, not transitive:
excluding A/B and B/C does not automatically exclude A/C. The app never restores an excluded choice just to fill four slots;
a small pool can yield fewer options, as with exact-title deduplication.

Curate these pairs from actual overlapping meanings and register, not merely shared tags or similar spelling. This mechanism
does not discover every synonym or guarantee semantic uniqueness for uncurated pairs. Earlier apps ignore this field.
The validator checks declaration shape and reference integrity; editorial review establishes which pairs belong in the list.

When to add one: a pair needs an exclusion when a learner could reasonably accept either `title` as the answer for either word
(for example あげる/くれる, 開く/開ける, 良い/いい). Titles that are exactly equal need none, because the app already keeps them apart.
Homophones such as 暑い/熱い need none either: the reading quiz asks for the reading of a written word and compares readings, and
the meaning quizzes show different titles. Work through the pairs in [confusable-words.md](confusable-words.md) when you add or
reword a `title`; declare the exclusion on one of the two cards.

## Strokes file

```json
{ "schemaVersion": 1, "kanji": "休", "source": "KanjiVG ...", "sourceRevision": "<commit>",
  "viewBox": [0, 0, 109, 109], "strokeCount": 6,
  "strokes": [ { "id": 1, "type": "㇒", "points": [[x, y], ...] } ] }
```

Optional `orderVariants` lists extra stroke orders the app accepts as clean. Each entry must be a different permutation of the
integers `1..strokeCount`, not the default order (e.g. `[[1, 3, 2]]` for three strokes). Edit `tools/order_variants.json`
(`{ "<char>": [[...]] }`) and run `generate_strokes.py`; only add orders backed by a source (MEXT 筆順指導の手びき, KanjiVG variants).

Strokes are listed in stroke order; each stroke is 16 points sampled by arc length from the KanjiVG path.
Validation also checks file/kanji identity, schema, numeric fields and point structure. Sixteen points is the generator's convention;
the importer requires at least two finite two-coordinate points per stroke.

## Grammar exercises

`grammar/<set-id>.json` files use `schemaVersion: 1` and contain stable construction, relationship and exercise IDs. Each exercise
has a Japanese prompt with exactly one `____` blank, an English translation, evidence from the context, an explanation,
the correct construction ID, accepted typed forms, and answer options with a rationale for every alternative. Every relationship
must have examples targeting each of its constructions. Its linked `article` must be an existing `articles/<slug>.md` file.

Author examples where context makes one choice clearly better than the closest alternative; do not include examples where both
forms are equally natural. Keep the evidence and rationale specific to the contrast, not just a definition of the answer. The
validator checks structure and references, not Japanese naturalness or grammatical accuracy, so grammar content needs editorial
review. Check the full inventory in the linked article, including constructions not offered as buttons: typed answers are not
restricted to the displayed multiple-choice alternatives. Reject an underdetermined item rather than use an unstated intended
nuance to make an otherwise natural alternative wrong.

The tested unit may be a grammatical function with equivalent realizations, not necessarily a single word. For example,
the foundations `non-necessary-inference` examples accept わけではない, ものではない and とは限らない where the completed
sentence expresses the same non-guarantee. They do not pretend to measure a distinction between those realizations.
Keep equivalent forms inside one answer class, never as competing buttons. Accept contracted and
kanji-written forms where appropriate to that sentence. An accepted form must preserve the tested meaning and fit the entire
completed sentence; do not import an equivalence into unrelated contexts. The validator rejects duplicate option labels and
distractors that collide with accepted answers after the app's trim/NFKC normalization.

A blank may ask for the diagnostic part of a construction whose stem is already printed. For example,
`写っているわけ____` tests the ending がない against にはいかない without falsely rejecting the whole-sentence alternatives
写っているはずがない or 写っていることはない. Option labels and accepted answers must contain only the missing span.
Explain such alternatives in the answer feedback; do not claim that the corresponding whole sentences are invalid.

The eight original exercises in `formal-nouns-pilot.json` retain their IDs and their construction/relationship identities.
`formal-nouns-foundations.json` adds three examples each for six functions, including the double negative 行かないわけにはいかない.
The [source record](grammar-foundations-sources.json) identifies the scope and inspected references. Broader article coverage is
being added in reviewed batches, not claimed by the existence of the schema. Keep source records free of personal progress exports.

`formal-nouns-actions.json` adds 12 exercises on ことができる, ことがある, ことにする and ことになる, with
[its own source record](grammar-actions-sources.json). The occurrence unit includes both past experience and occasional behavior;
the exercise ID and verb form distinguish the use. Decision questions explicitly request the act-of-deciding frame, rather than
pretend that a personal decision cannot also be announced as an arrangement. The printed こと／ことに stays outside the blank.

`formal-nouns-intent.json` adds nine exercises on intended meaning/representation, reasoned inference, and normative
judgment; see the [source record](grammar-intent-sources.json). The つもり examples here use noun + のつもりで, not every
future-plan or assumed-state construction. The inference target groups はず／よう in the selected sentences rather than claim
to measure a distinction between those forms. Normative answers group べき with other forms, including の／ん directives or
regret, only where the whole sentence supports that function. Accepted forms are not global substitution rules.

`formal-nouns-stages.json` adds nine exercises on the three basic ところ action stages: immediately before, during, and just
after an activity; see the [source record](grammar-stages-sources.json). Each stage uses the same three verbs in different
contexts. The question-side English explicitly asks for the given verb's dictionary, ている or た form; ところです is
already printed. Accept the literal missing form, including kana spellings and conversational てる／でる contractions.
This is a controlled stage/form contrast, not an unrestricted cloze or a test that たところ must exclude たばかり.
Do not move the form restriction into answer-only feedback or generalize these activity patterns to every use of ている.

`formal-nouns-states.json` adds six exercises contrasting たまま (retaining an action's result) with ないまま (leaving the
action undone), three per pattern; see the [source record](grammar-states-sources.json). The question-side instruction limits
the answer to the supplied verb's た- or ない-form, with まま already printed. Each verb appears on both sides of the contrast.
In particular, 消したまま keeps the lights off while 消さないまま leaves switching off undone; do not equate grammatical
polarity with an on/off state or a positive/negative evaluation. Noun/adjective and conformity uses of まま are not covered by
these exercises. Natural whole-sentence alternatives are not wrong merely because they fall outside this controlled task.

## Links and safety

- Links between imported pages are relative `.md` paths (`../words/大小.md`) so they also work on GitHub. The app turns them into in-app navigation with a back button.
  Relative links in imported content must target `kanji/`, `words/`, or `articles/`: `docs/` is not included in the content manifest.
- Other links must be `https://`. Raw HTML is not allowed. Text that names a kanji or word without a card is left as plain text.
- A word article must link (e.g. `[冗](../kanji/冗.md)`) every kanji listed in its `kanji:` field that has a card in `kanji/`; kanji without a card are exempt. `tools/validate.py` enforces this.
- Review state in the app is keyed by the kanji character, so don't rename cards; change `title` and body freely.
